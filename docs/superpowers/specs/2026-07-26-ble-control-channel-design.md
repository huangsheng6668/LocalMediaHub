# BLE 控制通道（并行稳定信令）设计

**日期**: 2026-07-26
**范围**: Android 端 (`android/app/src/main/java/com/juziss/localmediahub/`) + Go server 端 (`server/`)
**目标**: 在现有 Wi-Fi/HTTP 主通道之外，引入 BLE GATT 作为可选的、默认关闭的并行控制信令通道，提升控制类指令（播放控制、进度同步、选书）的稳定性；蓝牙不可用时零退化、零负优化。

---

## 1. 背景与现状

LocalMediaHub 当前传输架构：

- **Go server**：PC/笔记本（未来可能开发板）上运行的 HTTP server，持有媒体库，提供 REST API + 媒体字节流。
- **Android 客户端**：通过 Wi-Fi/HTTP 连接 server，消费媒体（视频流、图片、小说）。
- **Web 端**：浏览器访问 server，与 Android 平级消费方。

当前所有数据（媒体字节 + 控制信令）**全部走同一条 Wi-Fi/HTTP 通道**。痛点：

- Wi-Fi 抽风/丢包/高延迟时，**控制指令也被拖累**（用户点暂停，几百毫秒甚至秒级才响应）。
- 户外无路由器场景（手机直连 server 设备），完全无法连接。
- 离线时进度同步、阅读位置上报无法进行。

### 为什么选 BLE 而非其他

- **经典蓝牙 SPP**：带宽更高，但需系统级配对弹窗（用户无法静默通过），且 iOS 不支持 SPP，配对状态污染系统蓝牙列表。
- **Wi-Fi Direct**：带宽 = Wi-Fi 级（能跑视频），但 Android 兼容性参差、调试痛苦、复杂度高一个量级。
- **BLE GATT**：低功耗、无需系统配对、跨平台前景好、带宽足够覆盖控制信令（~100–400 KB/s 实测），首次连接无感。

**结论**：BLE 作为并行控制通道，媒体数据仍走 Wi-Fi，各取所长。

---

## 2. 核心设计原则

### 2.1 零负优化原则（最高优先级）

BLE 是**纯增量增强**，不是依赖：

- 蓝牙关闭 / 未授权 / 未连上 server → **完全走现有 Wi-Fi/HTTP，体验和现状一致，零退化**。
- 设计里**任何**"没蓝牙就跑不了"的环节都视为 bug。
- 用户不开蓝牙，功能、性能、体验**全部不变**；开了蓝牙只是"控制更稳"。

### 2.2 职责分工（并行模式）

| 通道 | 承载内容 | 数据特征 |
|---|---|---|
| **Wi-Fi/HTTP**（首选） | 媒体字节流（视频、图片、缩略图、封面、epub 全文） | 大数据、带宽敏感 |
| **BLE GATT**（降级） | 控制信令（始终）+ **小说单章文本**（仅 Wi-Fi 不可用时） | 小包 + 按需中等数据 |

**核心划分**：

- **控制信令**：BLE 为权威通道（详见 2.3）。
- **媒体数据**（视频/图片/缩略图/封面）：**永远走 Wi-Fi**，BLE 不承载。
- **小说文本**：**动态路由**——Wi-Fi 可用走 Wi-Fi（快），Wi-Fi 不可用时降级走 BLE（按单章传输，详见第 6 节）。

### 2.3 BLE 为权威控制通道

控制信令**单一权威来源**原则：正常运行时控制信令一律走 BLE，server 收到的控制只有这一个来源，无冲突。Wi-Fi 媒体流是"哑管道"，不携带控制状态。

## 3. 通道状态机

```
启动时（Android 端）：
  检测"BLE 实验性开关"是否开启
    └─ 关闭 → 纯 Wi-Fi 模式（控制+媒体都走 HTTP），与现状一致，结束
    └─ 开启 →
        检测蓝牙硬件可用性 + 用户是否授权 BLUETOOTH_SCAN/CONNECT
          ├─ 不可用/未授权 → 纯 Wi-Fi 模式（不报错、不打扰）
          └─ 可用且授权 → 后台启动 BLE scan，尝试发现 server
              ├─ 未发现/连接失败 → 纯 Wi-Fi 模式（后台静默重试发现）
              └─ BLE 连接成功 → 并行模式（Wi-Fi 媒体 + BLE 控制）

运行中：
  BLE 断开 → 自动降级，控制信令切回 Wi-Fi/HTTP，不报错、不中断用户操作
  BLE 恢复 → 控制信令切回 BLE，无感切换

文本资源请求（小说章节）时的路由：
  探测 Wi-Fi 健康（最近 RTT / 失败率）
    ├─ Wi-Fi 可用且健康 → 走 Wi-Fi/HTTP（快）
    ├─ Wi-Fi 不可用 + BLE 已连接 → 降级走 BLE 分章传输（慢但可用，详见第 6 节）
    └─ 两者都不可用 → 报错提示用户
```

**用户视角**：开不开蓝牙都能用，开了只是"控制更稳 + 户外能看小说"。BLE 断连对用户完全透明（除非用户主动查看连接状态）。

## 4. BLE 协议设计

### 4.1 角色分配

- **server（Go，PC/开发板）= Peripheral**：启动后常驻广播 GATT service。
- **Android 客户端 = Central**：扫描 → 连接 → 发现 service → 订阅 notify 特征。

语义清晰：服务提供方广播，符合"server 提供数据"。

### 4.2 GATT Service / Characteristic

定义一个自定义 service（128-bit UUID，项目内固定）：

| Characteristic | UUID 后缀 | 属性 | 方向 | 用途 |
|---|---|---|---|---|
| `Command` | `-CMD` | Write | Central → Peripheral | 客户端下发控制指令（播放/暂停/选书/seek） |
| `State` | `-STATE` | Notify | Peripheral → Central | server 广播当前状态（当前播放项、播放位置） |
| `Progress` | `-PROG` | Write + Notify | 双向 | 阅读进度/播放进度上报与下发 |
| `Chapter` | `-CHAP` | Write + Notify | 双向 | 小说单章文本请求（Central 写入章节 ID）+ 分块下发（Peripheral notify 文本块） |

> 具体 128-bit UUID 在实施阶段生成并固定写入两端常量。

### 4.3 指令格式

控制信令为小 JSON 或紧凑二进制（实施阶段定），典型指令：

- `{"op":"play_pause"}` / `{"op":"next"}` / `{"op":"prev"}`
- `{"op":"seek","pos":123.4}`（视频秒数）
- `{"op":"select","book_id":"abc","chapter":3}`
- `{"op":"reading_progress","book_id":"abc","position":0.42}`（全书进度 0~1）

每包 ≤ 20 字节（兼容默认 MTU），大包通过 MTU 协商到 247 后单包承载。MTU 协商失败时退回分包。

### 4.4 带宽预期（对齐）

| 负载 | 大小 | 通道 | BLE 传输时间（~200 KB/s 估算） |
|---|---|---|---|
| 控制信令 | 几十字节 | BLE | 瞬时，无感知 |
| 阅读进度同步 | < 100 字节 | BLE | 瞬时 |
| 小说单章正文 | 几十~几百 KB | BLE（仅 Wi-Fi 不可用时） | 单章 ~1–5 秒 |
| epub 全文 | 几 MB | **Wi-Fi**（BLE 不传全书，只按章传） | Wi-Fi < 1 秒 |
| epub 图片资源（插图） | 不定 | **Wi-Fi**（永不走 BLE） | — |
| 缩略图/封面 | ~200 KB | **Wi-Fi** | — |
| 视频/音频流 | 大 | **Wi-Fi**（BLE 带宽不够） | — |

**确认**：BLE 承载内容 = 控制信令（始终）+ 小说单章正文（仅 Wi-Fi 不可用时）。其余媒体数据**全部走 Wi-Fi**。

## 5. 关键工程约束

### 5.1 运行时蓝牙可用性检测

- 部分开发板无蓝牙模块 → BLE 通道**静默禁用**，不影响 Wi-Fi 主路径。
- 检测失败不抛错、不打断用户，仅记录日志。
- server 端 Go 启动时尝试初始化 BLE adapter，失败则不广播、不报错。

### 5.2 权限策略

Android 12+ 需 `BLUETOOTH_SCAN` / `BLUETOOTH_CONNECT` 运行时权限。采用**设置项触发**策略：

- BLE 功能作为**设置页里的可选实验性开关**，默认关闭。
- 用户主动打开开关时，才请求蓝牙权限。
- 用户拒绝授权 → 开关保持关闭，走纯 Wi-Fi，不再打扰。
- 不在 app 启动 / 首次进入功能时主动弹权限请求。

### 5.3 server 端 BLE 栈

- Go 端使用 `tinygo-org/bluetooth`（跨平台：Linux BlueZ / Windows / macOS）。
- 开发板（BlueZ）路径与 PC 一致，无需分支。
- 资源占用：BlueZ 守护进程常驻 ~20–40MB，开发板可接受。

### 5.4 穿墙/覆盖预期（不夸大）

- BLE 2.4GHz 低功耗，覆盖半径通常**小于** Wi-Fi 路由器（发射功率低）。
- 同一房间/隔一堵墙：BLE 体验良好。
- 隔两堵墙以上：BLE 也可能先掉线，但**自动降级到 Wi-Fi**，用户无感。
- BLE 的真正价值是**"无需路由器即可直连"**（户外/离线场景），而非穿墙。

## 6. 小说文本的 BLE 降级传输

当 Wi-Fi 不可用、BLE 已连接时，小说章节文本降级走 BLE。本章定义其传输机制。

### 6.1 传输单位：单章

- BLE 文本传输的**最小单位 = 单章**（非整本）。
- 客户端按需请求**当前章 + 预加载下一章**，不预取全书。
- 整本 epub 永远不经 BLE 全量传输。

### 6.2 不走 BLE 的文本内容

| 内容 | 走 BLE？ | 原因 |
|---|---|---|
| 小说单章正文（txt / epub 纯文本部分） | ✅ | 几十~几百 KB，分块可传 |
| epub 内嵌图片（封面、插图） | ❌ | 图片大，BLE 传图无意义；提示"此资源需 Wi-Fi" |
| 图片资源密集的章节（图多导致单章过大） | ❌ | 提示"此章需 Wi-Fi"，跳过 BLE 传输 |

### 6.3 分块传输协议

- 单章文本切分为固定大小块（默认 ~200 字节，配合 MTU 协商后单包承载）。
- 每块携带：`{chapter_id, block_index, total_blocks, payload}`。
- 接收方按 `block_index` 顺序重组，全部到齐后拼成完整章节。

### 6.4 信令优先级队列（防堵塞）

BLE 通道同时承载"控制信令"和"文本数据"时，**控制信令永远优先**：

- 写队列分两个优先级：
  - **高优先级**：控制指令（播放/暂停/seek/选书）—— 立即插队发送
  - **低优先级**：文本数据块 —— 排队发送，每发一块前检查高优先级队列
- 效果：即使正在传一章文本，用户点暂停也能**瞬时响应**，不被文本堵住。

### 6.5 断点续传

- BLE 传输中突然断开 → 已确认接收的块不丢。
- 重连后客户端告知 server 已收到的最大 `block_index`，从下一块继续。
- 块级 ACK 机制保证不重传已收部分。

### 6.6 传输进度 UI

- BLE 传文本较慢（单章 1–5 秒），客户端显示进度，避免用户以为卡死：
  - "正在通过蓝牙加载第 X 章... (45%)"
  - 支持取消（取消后丢弃未完成块，不写入）。

### 6.7 路由决策时机

- 仅在**用户打开章节**且**Wi-Fi 探测失败**时，触发 BLE 降级传输。
- Wi-Fi 探测使用轻量探针（最近若干次 HTTP 请求的 RTT / 失败率），避免在 Wi-Fi 半死不活时反复超时。
- 一旦 Wi-Fi 恢复健康，后续章节请求自动回到 Wi-Fi。

## 7. 不做什么（YAGNI）

明确**不纳入**本期范围：

- ❌ 经典蓝牙 SPP 通道
- ❌ Wi-Fi Direct 混合方案
- ❌ iOS 客户端（BLE 协议设计时保留跨平台可行性，但本期不实现 iOS）
- ❌ BLE 上传输图片/封面/缩略图/视频/音频（媒体数据永远走 Wi-Fi）
- ❌ BLE 全量传输整本 epub（只按单章传输）
- ❌ BLE 加密配对（信令非敏感数据，默认不触发系统配对；如未来需要再评估）
- ❌ 多 server / 多客户端并发连接（本期单 server 单客户端）

## 8. 测试策略

- **单元测试**：
  - BLE 状态机（启动检测、降级、恢复切换）纯逻辑层，不依赖真实硬件。
  - 文本路由决策（Wi-Fi 健康/不健康时的通道选择）。
  - 分块传输的重组 + 断点续传逻辑（用模拟块序列）。
  - 优先级队列：文本传输中插入控制指令，验证控制不被堵塞。
- **集成测试**：
  - 双通道一致性——BLE 断开瞬间控制信令切回 Wi-Fi，进度不丢/不抖。
  - BLE 文本降级：Wi-Fi 断开 → 章节正确从 BLE 传完 → Wi-Fi 恢复 → 下一章回 Wi-Fi。
- **手动验证**：PC server + Android 真机，覆盖：
  - 蓝牙关 → 纯 Wi-Fi，体验不变
  - 蓝牙开未连 → 纯 Wi-Fi，后台静默重试
  - BLE 连上 + Wi-Fi 正常 → 控制 + 文本都走各自通道
  - BLE 连上 + Wi-Fi 断 → 章节降级走 BLE，控制仍走 BLE，体验可用
  - BLE 运行中断开 → 控制切回 Wi-Fi，无中断
- **开发板验证**（未来）：无蓝牙模块的板子启动不报错。

## 9. 待实施阶段细化的点

- 128-bit UUID 具体取值（两端常量）
- 指令格式的 JSON vs 紧凑二进制最终选型
- MTU 协商失败时的分包协议细节
- 文本分块大小、块头格式、ACK 协议的最终取值
- Wi-Fi 健康探针的判定阈值（RTT 上限、失败次数）
- BLE scan / connect 的退避重试参数（间隔、上限）
- 设置页 UI 文案（"实验性"标注、状态指示）
